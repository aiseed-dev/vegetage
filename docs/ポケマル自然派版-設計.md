# DESIGN: ポケマル自然派版（自然派農家の紹介・予約プラットフォーム）

日付: 2026-08-20（同日、ドメイン・運営分離の方針を反映）
状態: 方針確定・実装未着手

## 目的・背景

自然な農法で育てた野菜や農体験(収穫体験・森の散策ガイドなど)を提供する農家と
消費者を直接つなぐ仕組みを構築する。
ポケットマルシェの本質(生産者と消費者の直接のつながり)を「蒸留」し、
決済を持たない最小構成で実現する。

最初の1軒のサイトをテンプレートの原型とし、2軒目以降に横展開する。

## ドメインと運営体制の分離(重要)

| ドメイン | 役割 | 運営 |
|---|---|---|
| aiseed.page | 野菜辞典(Vegetage 辞典、既存) | 現体制で長期管理を継続 |
| vegetage.dev | ポケマル自然派版(営業用サイト) | 将来は他者に運営を移管する前提 |

ブランド表記は「Vegetage」(e 綴り)に統一済み。vegetage.dev は Cloudflare
Registrar で取得。誤取得した vegitage.dev は 301 リダイレクト用に保持。

**運営移管を見据えた構成方針:**

- vegetage.dev 側のリソース(ドメイン、Pages、Workers、D1、メール送信)は、
  可能な限り**辞典側と分離した Cloudflare アカウント**に置く。Cloudflare は
  アカウント間の Workers/Pages 移動が容易でないため、最初から分けておくのが
  引き継ぎコスト最小。
- メール送信サービス(Resend 等)や Google OAuth クライアントの登録も
  vegetage の事業名義で行う。
- Sign in with Apple は Apple Developer Program の登録に依存する。移管時は
  運営者側での加入・Service ID 移行が必要になる点を認識しておく。
- vegetage.dev に掲載するプライバシーポリシー・運営者表記は、移管を想定して
  運営主体名で書く。

## 基本方針(決定事項)

| 決定 | 内容 |
|---|---|
| 決済は作らない | 通販は各農家の既存ECサイトへのリンクで対応 |
| 予約はリクエスト制 | フォーム送信 → 農家がメール返信で確定。空き枠の在庫管理は持たない |
| 連邦型アーキテクチャ | 各農家は独立した Cloudflare Pages サイト。vegetage.dev は紹介ディレクトリと中央APIを持つ |
| 農家サイトはテンプレート量産 | 農家に自作させない。共通テンプレートに AI で内容を流し込み、制作・デプロイを代行。農家は写真と文章を提供するだけ |
| フォーム UI は農家サイト内 | 中央フォームへの画面遷移はしない。UX は農家ドメインで完結 |
| 送信先は中央 API | フォームの POST 先は vegetage.dev の Workers。記録・通知・履歴を中央集約 |
| メール送信は中央提供 | 農家側に送信インフラ(固定 IP・SMTP 等)を一切持たせない |
| 消費者アカウントは次期 | Apple / Google ログインのみ。LINE ログインは使わない。登録は任意 |
| 作らないもの | 決済、配送管理、チャット、レビュー、消費者アカウント必須化 |

## 農家サイトテンプレート

- 技術: 軽量な静的サイト(HTML/CSS/JS または静的サイトジェネレータ)。
  Flutter は使わない。辞典アプリとは独立。
- **構造化データを標準装備**: 体験メニュー・所在地・料金・予約導線を
  schema.org 形式(JSON-LD)でマークアップする。旅行者側の AI エージェントが
  体験を探して予約する時代に「AI に読まれる直販サイト」であることが
  Vegetage の戦略ポジション(仲介層は AI に迂回されるため、ツアー事業への
  参入より AI 可読なデータ層になることを優先する)。
- 1 農家 = 1 Cloudflare Pages プロジェクト。独自ドメインまたは pages.dev。
- ページ構成:
  - トップ: 農家の物語(顔写真・畑・栽培哲学)
  - 出品一覧: 野菜セット・収穫体験・散策ガイドをカード形式で
  - 出品詳細 + 予約/問い合わせフォーム(フォーム UI はサイト内蔵)
  - 通販は既存 EC サイトへの外部リンク
- 法規制対応を標準の型として組み込む(体験メニューの前提):
  - 現地集合・現地解散(道路運送法・旅行業法を回避)
  - 収穫体験＋採れたて試食。調理提供はしない(食品衛生法の営業許可不要)
- フォームは中央 API へ fetch で POST。サイト自体にサーバー機能は持たない。

## 中央 API(vegetage.dev 側 Workers)

- `POST /inquiry`
  - 入力: farm_id, item_id, 名前, 連絡先, 希望日, 人数, メッセージ, Turnstile トークン
  - 処理: Turnstile 検証 → D1 に記録 → 農家へ通知メール → お客様へ受付確認メール
- CORS: 農家ドメインの許可リストで管理(テンプレート量産時にリストへ追加)
- D1 スキーマ(最小): inquiries(id, farm_id, item_id, name, contact, date_pref,
  party_size, message, user_id NULL, created_at)
- メール送信:
  - トランザクションメールサービス(Resend 等、無料枠)を Workers から呼ぶ。
    自前 SMTP サーバーは運用しない。
  - SPF / DKIM / DMARC は **vegetage.dev** に一度だけ設定。
    到達性・IP レピュテーションの問題を中央に集約し、農家側の設定をゼロにする。
  - 農家への通知は Reply-To をお客様アドレスに設定。農家は受信メールに
    返信するだけで、以降は vegetage.dev を経由せず直接やりとり。
  - 農家の受信は各自の既存メール(Gmail 等)。希望があれば Cloudflare
    Email Routing(無料)で独自ドメインアドレス → 既存メールへの転送を提供。

## 農家ディレクトリ(vegetage.dev)

- 静的構成。農家データの JSON を追加するだけ。
- ディレクトリ: 地域・品目・体験内容で探せる一覧 + 紹介ページ + 農家サイトへの外部リンク
- 辞典(aiseed.page)との相互リンク: 野菜の物語ページ →「この野菜を育てている農家」、
  農家紹介ページ → 辞典の該当品目。これが Vegetage 固有の集客動線。
  運営が分かれても、リンクは通常の外部リンクなので依存関係は生じない。

## 次期バージョン: ユーザー登録

- 認証: Apple / Google のソーシャルログインのみ(決定済み。LINE は使わない)。
- 登録は任意。ゲスト送信は常に可能。登録の価値は「入力の省略」と「問い合わせ履歴」。
- 農家サイト(別ドメイン)との連携はポップアップ方式:
  フォームの「Vegetage アカウントで入力を省略」ボタン → vegetage.dev の
  ポップアップで Apple/Google ログイン → トークンを postMessage で農家サイトへ
  返して自動入力。送信時に user_id を紐付け。ページ全体の遷移はしない。
- 変更箇所はテンプレート 1 箇所 + 認証 Worker 1 箇所に閉じる。
  既存農家サイトはテンプレート更新の再デプロイのみで対応。
- ユーザーデータを預かるため、プライバシーポリシーの掲載が必要になる
  (決済がないため特商法表記は不要のまま)。

## フェーズ計画

1. **フェーズ 1(現行)**: vegetage.dev 取得・営業サイト開設、農家サイトテンプレート +
   最初の農家サイト制作・公開、中央 API(inquiry + メール)、農家ディレクトリ。認証なし。
2. **フェーズ 2(次期)**: Apple / Google ログイン、入力自動化、問い合わせ履歴。
3. **フェーズ 3(体制)**: 運営の他者移管(Cloudflare アカウント・メール送信・
   プライバシーポリシーの主体変更)。決済は作らない方針を維持。

## コスト

- メール送信サービス: 無料枠内(規模拡大時のみ有料)
- 固定費: vegetage.dev / vegitage.dev のドメイン代(各年13ドル前後)と
  各農家の独自ドメイン代のみ(pages.dev 利用ならゼロ)
